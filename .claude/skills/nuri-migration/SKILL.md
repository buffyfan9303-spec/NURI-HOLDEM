# nuri-migration — 라이브 Supabase 안전 마이그레이션

운영 중인 DB다. 아래는 실제로 크리티컬 버그(fail-open 권한)가 터졌던 경험에서 나온 규칙이다. 전부 지켜라.

## 0) 적용 경로 — **이것만 쓴다** (2026-09-15 확립 · 2026-09-16 재확인)

🔴 **`supabase db push` 는 이 저장소에서 못 쓴다.** CLI 가 파일명 규칙(`20260915f_…`)을 `<timestamp>_name.sql` 이 아니라고
**전부 건너뛴다.** CLI 이름으로 바꿔 시도하면 "원격 이력 350여 건이 로컬에 없다"며 `migration repair` 를 시킨다 —
**절대 하지 마라.** 로컬 파일과 원격 이력은 애초에 따로 관리돼 왔다.

🔴 **Supabase 브랜치도 못 쓴다.** 브랜치는 `supabase_migrations.schema_migrations` **기록**으로 스키마를 다시 만드는데,
이 저장소는 MCP 로 직접 적용해 와서 **기록이 어긋나 있다**(2026-09-15 실측 357건 · 파일명 규칙도 기록 형식과 다르다).
→ 브랜치를 만들면 **보안 구멍이 아직 열려 있는 옛 스키마**가 나온다. 게다가 유료다(`get_cost` 실측 **$0.01344/시간**).

👉 **절차**
1. `supabase/migrations/` 에 파일을 만든다(기존 파일명 규칙 그대로).
2. **MCP `execute_sql` 로 그 내용을 직접 적용**한다. 길면 **논리 단위로 2~3부에 나눠** 적용하고 부마다 확인한다.
3. 자가검사 결과를 확인한다(§5).
4. 파일 머리에 **"✅ YYYY-MM-DD 라이브 적용 완료 + 실측값"** 을 적고 **커밋한다.**
   ⚠ 2026-09-16 실측: `20260915g·h·i·j·k` 다섯 파일에 이 표기가 **하나도 없었다.** 표기가 없으면 다음 사람이
   '적용 안 된 줄 알고' **다시 적용**한다. 파일 머리말이 곧 적용 상태의 정본이다.


## 1) 권한(ACL) — 가장 위험한 지점
- 관리/민감 RPC는 **`REVOKE ALL ON FUNCTION ... FROM PUBLIC;`** 이 필수다.
  ⚠️ `REVOKE FROM anon`만으로는 **무효** — PUBLIC 기본 GRANT 때문에 anon이 여전히 실행 가능하다. 반드시 `FROM PUBLIC`.
- 회수 후 필요한 롤에만 재부여: `GRANT EXECUTE ON FUNCTION ... TO authenticated;`
- ⚠️ **2026-09-12 실측 정정** — 예전에 여기 "`CREATE OR REPLACE FUNCTION`은 ACL을 초기화한다"고 적혀 있었는데 **사실과 반대**다.
  격리 컨테이너(**postgres:17** — 운영 실측 17.6) 4단계 실측: 새로 만든 함수는 anon 실행 **가능**(PUBLIC 기본 GRANT) → `REVOKE` 후 불가 →
  **`CREATE OR REPLACE` 뒤에도 그대로 불가(ACL 보존)** → **`DROP` 후 재생성하면 다시 가능(ACL 초기화)**.
  즉 ACL이 날아가는 것은 **`DROP` + 재생성**이다(반환 타입 변경이 그 경우다). 그때는 REVOKE/GRANT를 **반드시 다시** 쓴다.
  `CREATE OR REPLACE`에도 REVOKE/GRANT를 같이 적어 두는 관행은 유지한다 — **함수가 새로 만들어지는 경우**에 필요하기 때문이다.
- ⚠️ **이 차이 때문에 자가검사가 거짓 통과한다**: 이미 REVOKE된 함수를 `CREATE OR REPLACE`로 덮으면
  **파일에서 REVOKE를 빼도 ACL이 남아 검사를 통과한다**(2026-09-12 §8-2에서 실제로 밟았다).
  ACL 자가검사를 음성 대조할 때는 **`DROP` 후 적용**해야 한다.

## 2) SECURITY DEFINER
- 모든 SECURITY DEFINER 함수는 `SET search_path = public, pg_temp` 고정(하이재킹 방지).

## 3) NULL-safe 가드 (fail-open 방지)
- 권한 체크는 **`IS DISTINCT FROM`** 을 써라. `my_role() <> 'admin'`은 비로그인(auth.uid()=NULL)에서 `NULL<>'admin' = NULL`이 되어 if를 건너뛰고 가드가 열린다.
- 예: `IF my_role() IS DISTINCT FROM 'admin' THEN RAISE EXCEPTION ...`

## 4) 멱등·비파괴
- `CREATE TABLE/COLUMN IF NOT EXISTS`, `DROP ... IF EXISTS`.
- 반환 타입 변경은 `DROP FUNCTION` 후 재생성 — 이때 ACL 복원 잊지 말 것.
- 기존 행에 0px 영향인지 확인(신규 필드는 optional·폴백=현행값).

## 5) 검증
- 적용 후 **어드바이저 보안 ERROR 0** 유지 확인.
- **⭐ 운영 DB 트랜잭션 롤백 리허설** — 브랜치보다 정확하고 **공짜**다. 라이브 스키마·라이브 RLS 위에서 통째로 시험하고 되돌린다.
  ```sql
  begin;
    <마이그레이션 전문>
    do $$ ... 행동 검증 ... $$;
  rollback;
  ```
  · **먼저 롤백이 듣는지부터 확인해라** — 프로브 테이블을 만들고 rollback 뒤 `information_schema` 로 0 을 본다.
  · **사용자를 흉내 내는 법**(RLS 를 진짜로 시험하는 유일한 방법):
    `perform set_config('request.jwt.claims', json_build_object('sub', <uuid>,'role','authenticated')::text, true);`
    정책까지 태우려면 `set local role authenticated;` … `reset role;` 로 감싼다.
    **빈 문자열로 되돌리면 `auth.uid()` 가 NULL = 비로그인** — fail-open 검사에 반드시 넣어라.
  · 🔴 **음성만 검사하지 마라.** '무권한자 차단' 만 보면 *아무도 통과 못 하는* 고장도 통과한다.
    **양성 대조**(업주는 여전히 통과 · 위임하면 통과)를 같이 넣어라.
  · 🔴 **시험 대상 계정을 아무나 고르지 마라.** 2026-09-15 에 내 시험이 두 번 틀렸고 코드는 멀쩡했다 —
    (1) '다른 매장으로 안 번진다' 시험에서 고른 사용자가 **그 매장의 업주**였다(profiles 4명 중 3명이 매장 소유자다),
    (2) '본인 급여 조회' 가 0행이었는데 그 계정이 **그 매장 소속이 아니었다**(올바른 차단이었다).
    → `select id, role, (select count(*) from venues v where v.owner_id = p.id) from profiles p` 한 줄로 **역할·소유·소속을 먼저 조회**하고 골라라.
  · 🔴 **실패한 검증에서 먼저 물을 것은 "코드가 틀렸나"가 아니라 "테스트가 맞나"다.**
- `_`로 시작하는 내부 함수는 anon/authenticated에서 REVOKE(직접 호출 차단).

## 5-1) 적용 전 실측 — 추정으로 적지 마라
- **`select version();` 을 먼저 돌린다.** 마이그레이션이 쓰는 함수의 하한을 그 출력으로 확인한다.
  예: `20260913a` 의 판정기는 `regexp_instr` 을 쓰는데 이건 **PG 15+ 에만 있다**(`regexp_matches`·`regexp_split_to_array` 는 옛 버전에도 있다).
  **운영 PG 버전을 문서·기억·추정으로 적지 마라** — 편집기에서 한 줄 돌리면 끝난다.
- 파일이 바꿀 대상이 **라이브에 실제로 몇 개 있는지**를 쓰기 없는 미리보기로 먼저 센다. 저장소의 정의와 라이브 정의는 다를 수 있다.

## 5-2) 텍스트를 프로그램으로 고치는 마이그레이션 (2026-09-13 `20260913a` 재설계에서 얻은 것)

함수 본문(`pg_get_functiondef()`)을 스크립트로 일괄 수정하는 부류다. 여기서 실제로 밟은 것만 적는다.

- **정규식으로는 코드와 주석·문자열을 가를 수 없다.** `--` 주석 안, `'...'` 리터럴 안, `$$…$$` 달러쿼트 안의 글자가
  전부 똑같이 매칭된다. → **비코드 구간 마스킹(같은 길이 공백으로 치환)이나 토크나이즈가 먼저**고, 판정은 그 위에서 한다.
  (`20260913a` 의 `pg_temp.nuri_mask_noncode()` 가 이 역할이다.)
- **미리보기·게이트·치환·자가검사는 반드시 같은 판정기 함수를 호출해야 한다.** 각 단계에 정규식을 **복붙하면 어긋난다** —
  미리보기가 보여준 건수와 실제로 바뀌는 건수가 달라지는 순간 그 마이그레이션은 신뢰할 수 없다.
- **확신할 수 없으면 건드리지 않는다.** 자동 치환은 **가를 수 있다고 증명한 좁은 형태**로만 하고,
  나머지는 **원문 줄과 함께 "검토" 로 보고만** 한다. 진짜 가드처럼 보여도 그렇다.
  (전 판은 CASE 의 `when` 을 자동 치환했다가 SQL CASE **식**의 필터까지 바꿨고, 2026-09-13 독립 검증이 그 회귀를 잡았다.
  같은 날 다른 자리에서는 자동 치환이 NULL 세션의 읽기를 **1행 → 5행으로 넓혔다** — 가드가 아니라 필터였다.)
- ⚠ **`RAISE NOTICE` 는 Supabase SQL 편집기에서 안 보일 수 있다.** 사람이 반드시 봐야 하는 것(검토 건)은
  **`RAISE EXCEPTION` 으로 멈춰라.** "출력에 경고를 찍었으니 봤겠지" 는 성립하지 않는다.
  계속 진행은 명시적 승인 토큰으로만(`set local nuri.ack_review = 'on'`) — **승인해도 검토 건은 손대지 않는다**.
- ⚠⚠ **자가검사가 치환과 같은 판정기를 쓰면, 판정기 자체의 결함은 파일이 스스로 볼 수 없다.**
  "치환 후 자동 0건" 은 판정기가 옳다는 전제에서만 의미가 있다. 판정기가 애초에 못 보는 형태는 치환 전에도 0건이라 통과한다.
  → 판정기를 검증하려면 **격리 컨테이너(**postgres:17** — 운영 실측 17.6) 하네스**에 알려진 입력·기대 출력을 넣고 판정기만 따로 돌려야 한다.
  라이브에 적용하며 확인하는 것은 검증이 아니다.

## 6) 기록
- 라이브에 적용한 마이그레이션은 **① 파일 머리의 "✅ 적용 완료" 표기**와 **② `docs/HANDOFF.md`** 두 곳에 남긴다.
  ⚠ **에이전트 메모리에 적지 마라 — `.gitignore:62` 라 계정을 못 넘는다.** claude-A / claude-B 가 같은 저장소를 쓰므로
  git 에 없는 기록은 상대에게 **존재하지 않는 것**이다(HANDOFF §0-a).
- app_settings는 read=true 공개라 비밀키 저장 금지 — 비밀은 secret_settings(RLS 전면잠금, service_role 전용).

## 무료 한도 인지
- egress 5GB/월이 실질 천장. 실시간 구독은 '보는 화면'에서만 연결(게이팅). Storage 업로드 cacheControl 1년.
- Realtime Free tier: 동시연결 200·월 200만 메시지 — 프레즌스/타이핑 남발 시 TV 클락 구독까지 열화.

## 이 스킬이 못 보는 것
- **라이브의 실제 정의** — 저장소 SQL 을 읽어도 라이브 함수 본문이 같다는 보장은 없다. 미리보기(쓰기 없음)로 매번 확인해라.
- **판정기 자체의 결함** — 위 5-2 마지막 항목. 격리 컨테이너 하네스 없이는 파일이 스스로 못 본다(`nuri-verify` 의 음성 대조 원칙과 같은 문제다).
- **적용 후 클라이언트 쪽 영향** — RLS 를 좁히면 프런트의 변이가 에러 없이 **0행**으로 조용히 실패한다. 그 탐지는 `nuri-affect`.
- **DB 밖의 회귀** — 타입·빌드·테스트는 여기서 안 본다.

마무리는 반드시 `nuri-ship` 게이트로.
