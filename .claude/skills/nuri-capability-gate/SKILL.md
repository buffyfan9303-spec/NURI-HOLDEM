# NURI 실행 준비 점검

## 실제 환경부터 확인

실제 Git 루트·현재 프로필·버전·기존 diff·진행 기록을 확인한다. 프로필 경로와 로그인 계정은 별개다. 비밀키/토큰/쿠키/개인정보 값은 출력하지 않는다.
도구는 `발견 → 등록 → 활성 → 연결 → 이번 작업 실사용 검증`을 구분해 기록한다. Codex/Cursor/Claude Code의 도구 목록과 인증은 서로 자동 공유되지 않는다. 캐시·예제·옛 버전을 활성 설치로 세지 않는다.
이전 목록은 출발점일 뿐이다. 활성 프로필의 현재 등록과 실제 가벼운 읽기 전용 호출로 필요한 도구만 재확인한다. 원격 권한이 없으면 설치 성공과 연결 실패를 분리한다.

## 작업에 맞게 선택

기존 코드·네이티브 기능·설치된 도구가 해결하면 새 패키지를 추가하지 않는다. 필요한 스킬은 SKILL.md 전체와 지정 필수 참조를 직접 읽고 작업 ID와 연결한다. 모든 스킬 본문을 매번 적재하지 않는다.
관련 프로젝트 스킬: 편집 nuri-edit, 영향 범위 nuri-affect, 정본 nuri-single-source, 시간 nuri-time, DB nuri-migration, 보안 security-audit, 테스트 nuri-e2e/nuri-verify, 출시 nuri-ship. 실제 존재를 확인한다.
디자인 플러그인의 미감 제안은 현재 제품·자연스러운 한국어·접근성·실제 데이터·다크/라이트 요구에 맞는 것만 쓴다. 가짜 후기/활동/숫자, 타사 색/브랜드 복제, 불필요한 프레임워크 교체는 하지 않는다.
누락된 필요한 로컬 도구는 기존 출처·버전·권한·충돌·제거법을 검토해 지정 범위에 설치하고 무해한 점검을 한다. 로그인·유료 옵션·운영 연결 변경·키 복사는 자동 처리하지 않는다.

## 팀과 모델

정본 정책은 `.claude/rules/nuri-team-capabilities.md`다. 사용자 요청과 실제 도구 제공 범위가 우선한다.
네이티브 팀에는 실행 ID·팀원·요청/관찰 모델·직접 메시지 왕복·작업 소유권 증거가 필요하다. 역할 파일이나 패널만으로 팀 성공을 판정하지 않는다.
낮은 모델은 목록/요약/기계적 점검, Sonnet은 저위험 명확한 구현, Opus는 조정, Fable 5.1은 고위험 판단·중요한 시각 해석·복잡한 디버깅·첫 재발에 배정한다. 실제 모델이 다르면 표시한다.
자기 보고만으로 모델/성공을 증명하지 않는다. 공급자 대체·지원 불가·한도·추가 결제는 분리하며 강제 재시도/무단 계정 전환하지 않는다.
같은 체크아웃 단독 편집자, 독립 검증자, 브라우저/서버/테스트 데이터 소유권을 지정한다. 완료 전 구현자와 연동 상대가 직접 계약을 확인한다.

## 실행용 Markdown에 넣을 최소 항목

- 실제 폴더, 사용자 시작 명령과 에이전트 실행 지시의 구분, 기존 작업 이어받기.
- 기존 요구사항 ID, 필요한 스킬/플러그인/커넥터와 적용 또는 생략 이유.
- 작업별 역할·요청 모델·관찰 방법·권한·선행 작업·통과 기준.
- 실화면/독립 테스트/연동 테스트, 재발 처리, 종료 조건, 막힌 작업.
- `도구 / 출처·버전 / 프로필·범위 / 상태 / 관련 작업 / 실제 증거 / 미검증 이유` 표.
- `요구 ID / 변경·원인 / 구현자·관찰 모델 / 독립 검증자 / 명령·종료 코드 / PASS·FAIL·BLOCKED·NOT_RUN / 증거 경로` 표.

질문은 필요한 사용자 선택만 모아 표시하고 독립적인 안전 작업은 계속한다. 로컬 완료를 운영 검증·배포 완료로 보고하지 않는다. 새 교훈은 재현 증거가 있는 프로젝트 규칙/테스트로 제안하고, 자기 권한·정책을 자율 완화하지 않는다.
